▶ 1.1 Claude API Fundamentals D1 27%D4 20%

Messages API Structure

Claude is stateless. Every call gets: system prompt + full conversation history + current request. There is no server-side memory — you send everything, every time.

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system="You are a senior Java architect...",   # role, constraints, format
    messages=[
        {"role": "user",      "content": "..."},
        {"role": "assistant", "content": "..."},   # history injected by you
        {"role": "user",      "content": "..."},   # current turn
    ]
)
Exam trap: Tool results go in with role="user" NOT role="tool" or role="assistant". This is the most-tested D1 detail.

Streaming vs Non-Streaming

Use streaming when…Use blocking when…
Web chat UI (React, browser)Batch extraction pipelines
TTE (time-to-echo) matters for UXInternal APIs, latency not visible
Long responses (avoid timeout)Need complete response to parse JSON
Project tie-in: ConversationController.java uses Spring Boot SseEmitter for token-by-token SSE delivery. Tokens are JSON-encoded (objectMapper.writeValueAsString(token)) because raw \n in SSE data: fields is treated as event separator — breaks newlines silently.

Stop Sequences, Temperature, Top-P

ParamExam relevanceCommon mistake
temperature=0Deterministic → extraction pipelinesUsing temp to fix bad outputs (fix prompt instead)
stop_sequencesCut off before tool recursionConfusing with tool_choice constraints
max_tokensCritical — prevents runaway agentsToo low cuts off; too high wastes cost
top_pRarely tested; prefer temperatureMixing with temp without understanding interaction

Context Window Budget

Total window:          200K tokens (Claude 3.5 Sonnet / Haiku)
System prompt:         ~500 tokens
Tool descriptions:     ~300 tokens
Reserved for response: ~4K tokens

Available for history: ~195K tokens
Practical budget:      ~195K × 0.85 = ~165K (leave safety margin)
▶ 1.2 Prompt Engineering for Production D4 20%

System Prompt Layers

Layer 1: Role & Identity   → "You are a customer support specialist..."
Layer 2: Task & Goal       → "Your goal is to resolve issues accurately..."
Layer 3: Constraints       → "Never make refunds. Don't fabricate information."
Layer 4: Output Format     → "Respond in this JSON: {...}"
Layer 5: Few-shot (opt.)   → Only when task is genuinely ambiguous

Few-Shot Examples: When to Use

  • Task is ambiguous — example clarifies edge cases
  • Example prevents a specific common error
  • You've measured it actually improves accuracy
  • Task is well-defined (translation, summarization)
  • Just adding examples "for safety" — costs tokens, adds noise

Prompt Injection Vectors & Mitigations

# DANGEROUS: user data bleeds into system authority
system = f"Helping {username}. Data: {user_data}"

# SAFE: clear boundary between system authority and user data
system = "You are a helpful assistant."
messages = [{"role": "user", "content": f"Context: {user_data}\n\nQuestion: ..."}]
  • Document injection: Mark boundaries clearly. Never stuff full PDF into system prompt.
  • Dynamic tool schemas: Pre-define all tools in code, never build from user input.
  • Mitigation: Validate and sanitize anything entering context from external sources.

Forcing Deterministic JSON Output (D4 critical)

# ❌ WRONG — system prompt "return JSON only" fails ~5% of time
json.loads(response.content[0].text)

# ✅ RIGHT — use tool_choice to structurally enforce schema
response = client.messages.create(
    tools=[{"name": "extract", "description": "...", "input_schema": {...}}],
    tool_choice={"type": "tool", "name": "extract"},  # structural enforcement
    messages=[...]
)
data = response.content[0].input  # always valid JSON, schema-guaranteed
Key insight: tool_choice enforcement > system prompt instructions. System prompts are prose (Claude can drift). Tool choice is structural (Claude can't bypass it).

Validation Retry Loop (Not Blind Retry)

for attempt in range(3):
    response = claude.extract_json(prompt)
    try:
        data = json.loads(response)
        validate_schema(data)
        return data
    except (json.JSONDecodeError, ValidationError) as e:
        if attempt < 2:
            prompt += f"\n\nPrevious attempt failed: {e}\nFix and retry."
        else:
            raise  # escalate after 3 attempts
Tell Claude what broke. Blind retries with identical prompts produce identical failures.
▶ 1.3 Claude Code — Agentic CLI D3 20%

What It Is (Not Just Autocomplete)

Claude Code is a full agentic loop in a CLI. It reads files, edits code, runs shell commands, and iterates — not just autocomplete. It uses CLAUDE.md as "project memory".

CLAUDE.md Hierarchy (highest priority first)

1. .claude/commands/{cmd}.md  — command-specific frontmatter overrides
2. {module}/.claude/CLAUDE.md — module-level (e.g. frontend/)
3. ./CLAUDE.md                — project root (this project's CLAUDE.md)
4. ~/.claude/CLAUDE.md        — user global defaults
This project's CLAUDE.md is a live example: it lists build commands, ADRs, key constraints (never edit applied Flyway migrations, BIT(1) for booleans, etc.). That's what a production CLAUDE.md looks like.

What Belongs in CLAUDE.md

# CLAUDE.md
## Build Commands
- `./gradlew.bat bootRun` — start Spring Boot locally
- `npm run dev`            — admin-ui dev server on :3000

## Key Constraints
- Never edit applied Flyway migrations (V1–V5 are locked)
- BIT(1) not TINYINT for boolean columns (Hibernate 6 / MySQL8Dialect)
- JWT secret must be Base64-encoded, ≥256 bits

## Architecture
Spring Boot (:8080) → nginx proxy (:8081) → OpenRouter → MySQL (:3309)

Custom Slash Commands

--- # .claude/commands/review.md
description: "Pre-landing code review"
allowed-tools:
  - read
  - grep
  - diff
model: claude-sonnet-4-6   # can override per command
---

Review the changed files. Check SQL safety, auth gaps, lazy loading...
Use $ARGUMENTS for target path.

Hooks (Structural Safety Gates)

#!/bin/bash
# .claude/hooks/guard-destructive.sh — wired to PreWriteFile
if [[ "$1" =~ ^rm\ -rf ]]; then
  echo "BLOCKED: Destructive command. Ask user first." && exit 1
fi
Exam trap: CLAUDE.md is guidance, not enforcement. Hooks (PreWriteFile, PostToolUse) are enforcement. A constraint that "must never" happen needs a hook, not just CLAUDE.md text.

Claude Code in CI/CD (Non-Interactive)

# GitHub Actions — headless mode
- name: Claude Code Review
  run: |
    claude -p --allowedTools=read,grep,diff << 'EOF'
    Review PR files for SQL injection risks and missing auth checks.
    Files: ${{ github.event.pull_request.files }}
    EOF
  • --allowedTools=* in CI for convenience — dangerous, grants everything
  • Minimal explicit whitelist: --allowedTools=read,grep
  • Hooks as safety gates even in CI
▶ 1.4 Model Context Protocol (MCP) D2 18%

Architecture

Claude (client) ←── JSON-RPC over stdio / HTTP ──→ MCP Server
                                                    (GitHub, Jira, your API)

Tool:     Claude can CHANGE STATE (create issue, write file)
Resource: Claude can READ/REFERENCE (codebase, wiki page)

Tool Schema Golden Rules

{
  "name": "search_documents",         // verb_object convention
  "description": "Search internal docs by keyword. Returns snippets matching query.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "Search keywords (e.g. 'rate limiting strategy')"
      },
      "region": {
        "type": "string",
        "enum": ["NORTH","SOUTH","EAST","WEST"],  // enums > free strings
        "description": "Geographic filter"
      }
    },
    "required": ["query"]  // explicit, never rely on defaults
  }
}
Project tie-in: PUT /api/user/models/{id}/toggle uses integer PK, not string modelId. Model IDs contain / (e.g. meta-llama/llama-3.3-70b:free). Tomcat normalizes %2F before Spring MVC sees it — design tools around transport constraints.

tool_choice Values (Critical)

ValueBehaviorUse case
"auto"Claude MAY or MAY NOT use toolsOpen-ended tasks
"any"Claude MUST use at least one toolForce tool invocation
{"type":"tool","name":"X"}Claude MUST use tool X onlyStructured extraction, forced schema
Exam trap: "auto" and "any" are NOT the same. "auto" = optional. "any" = forced. For extraction pipelines: always {"type":"tool","name":"extract"}, not "any".

MCP Config Scoping

# Priority order (higher = wins)
1. .mcp.json (project root)    ← project-specific tools
2. ~/.claude.json (user global) ← shared tools (GitHub, Slack)

# Credentials — never hardcode
{
  "tools": {
    "github": { "token": "${GH_TOKEN}" }  // ✅ env var
  }
}
// NOT: "token": "ghp_abc123..."           // ❌ hardcoded = security breach

Tool Count Limit

Recommended: 4–5 tools per MCP server. Each tool description consumes tokens. At ~20+ tools, Claude's ability to pick the right one degrades. Solution: split into multiple domain-specific servers (mcp-github, mcp-jira, mcp-internal).

Error Contract in Tool Results

{
  "type": "tool_result",
  "tool_use_id": "tool_abc123",
  "content": "Error: DB timeout. Index rebuilding. Retry in 60s or use cached list.",
  "is_error": true
}
// is_error=true + transient message → Claude knows it CAN retry
// is_error=true + "Invalid API key" → Claude knows it CANNOT retry
▶ 1.5 Agentic Patterns — ReAct, Orchestration, Failure D1 27%

The Core ReAct Loop (stop_reason is the key)

messages = [{"role": "user", "content": user_input}]

while True:
    response = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=1024,
        system=system_prompt, tools=tools, messages=messages
    )

    if response.stop_reason == "end_turn":
        return extract_text(response.content)  # done

    elif response.stop_reason == "tool_use":
        # Step 1: append Claude's response (with tool_use blocks)
        messages.append({"role": "assistant", "content": response.content})

        # Step 2: call each tool, append results
        for block in response.content:
            if block.type == "tool_use":
                result = dispatch_tool(block.name, block.input)
                messages.append({
                    "role": "user",           # ← CRITICAL: role="user" not "tool"
                    "content": [{
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": str(result),
                        "is_error": isinstance(result, Exception)
                    }]
                })
        # loop back to get next response

    else:
        raise RuntimeError(f"Unexpected stop_reason: {response.stop_reason}")

Sequential vs Parallel Tool Calls

# SERIAL — Claude issues tools one at a time (slow if independent)
# Tool A → wait → Tool B → wait → Total: sum of latencies

# PARALLEL — Claude issues multiple tool_use blocks in one response
# response.content = [tool_use_A, tool_use_B, tool_use_C]
# You call ALL THREE, then append ALL results, then loop back
# Total: max of individual latencies (not sum)

Prompt Claude for parallel behavior: "You have tools X, Y, Z. Call all of them simultaneously to resolve this quickly."

Orchestration Patterns — Router · Pipeline · Parallel

PatternWhen to UseKey Question
ROUTERMultiple independent tasks need different specialists"Are these tasks completely separate? Can I delegate each to a different agent?"
PIPELINESequential steps where each depends on the previous"Does step B need output from step A? Does step C need both A and B to complete first?"
PARALLELMultiple independent tasks that don't depend on each other"Can all these tasks run at the exact same time without blocking each other?"
  • ROUTER = task-level delegation ("send refunds to Returns Agent, billing to Billing Agent")
  • PIPELINE = sequential gates ("validate → check policy → process → confirm")
  • PARALLEL = concurrent execution ("search, read, analyze all at once")

Multi-Agent Hub-and-Spoke

          [Orchestrator]  — plans, delegates, aggregates
          /      |       \
    [Research] [Analyst] [Writer]
    subagent 1  subagent 2  subagent 3
    (search     (compute    (format
     tools)      tools)      tools)

Rules:
✓ Orchestrator delegates via messages, not tool exposure
✓ Subagents have isolated context — don't see each other
✓ Subagents don't call each other (creates loops)
✗ Orchestrator does NOT have all subagent tools (defeats isolation)

Failure Recovery Strategy

FailureWrong approachRight approach
Tool timeoutImmediate retry (hung tool stays hung)Mark as failed, continue with partial info
Auth errorRetry (won't fix itself)Fail gracefully, surface to user
High-value decisionLet agent guessEscalate to human with context
Repeated failureLoop foreverCircuit breaker: stop after N failures

Escalation — The Core Rule

When the agent stops and hands off to human:

  • Authority boundary exceeded — "I can approve up to €100, but this is €500"
  • Policy ambiguity — "The rule doesn't clearly cover this situation"
  • Risk signal detected — fraud indicator, legal issue, or angry customer

When NOT to escalate:

  • Situation is within agent's clear authority
  • Policy clearly covers it
  • No risk signals present
Golden Rule: Programmatic constraints beat natural language instructions. If your system prompt says "try to resolve" but the agent has no authority or information to resolve, the agent must escalate anyway.

When NOT to Use an Agent

  • A single well-prompted API call is sufficient (agent adds latency, cost, complexity)
  • Task is deterministic and stateless (no iteration needed)
  • Blast radius of autonomous actions is too high (ops/production changes)
Phase 5.0 — Gateway Intelligence Agent (live example): POST /api/agent/chat is a production ReAct loop built on this gateway. Two tools: get_model_status (reads model config from DB) and get_gateway_stats (reads usage stats). Retry candidate list — requested model first, then all DB-enabled models. Streams event: status progress SSE events during retries. Admin-only + BYOK required. MAX_TURNS=10 hard guard. This is §1.5 patterns implemented end-to-end in Java — study AgentService.java and OpenRouterAdapter.java alongside these patterns.
▶ 1.6 Safety, Reliability & Security D5 15%D1 27%

Rate Limiting Strategy (Project Reference)

Global limit:              "500 req/day total" — one user burns all quota
Per-user limit:            "50 req/day per user" — fair but unlimited tokens
Per-user + token budget:   "50 req/day + 1M tokens/day per user" — correct model
Per-user + model-specific: "50 calls/day to Opus, 200 to Haiku" — cost gates
This project: Bucket4j token-bucket per-user sliding window. Two separate limits: request_count (checked pre-call) and token_count (checked post-call). Request limit is pre-call because tokens are unknown before completion.

Audit Logging (What to Capture)

Every LLM call must log:
1. WHO:     user_id, API key hash (never plaintext key)
2. WHAT:    model, system_prompt_hash, input_tokens
3. WHEN:    timestamp (UTC)
4. OUTCOME: stop_reason, output_tokens, cost_usd
5. TOOLS:   list of tools invoked (if any)
This project's chat_logs table: captures user_id, model, tokens_input, tokens_output, status, response_preview. Flyway-managed schema — versioned, auditable.

Graceful Degradation Tiers

Tier 1 (User error):     Invalid input → clear error to user
Tier 2 (Service error):  DB timeout → retry 3x, then fail gracefully
Tier 3 (LLM down):       API unavailable → serve cached response or queue
Tier 4 (Budget exceeded): Rate limit hit → explain limit, reset time, next steps

AES-GCM vs BCrypt — Know the Difference

AlgorithmUse forWhy
BCryptPasswords (one-way)Verify only, never recover. Attacker can't decrypt even with key.
AES-GCMAPI keys (reversible)Must decrypt to use. BCrypt here = keys permanently unusable.
This project: ENCRYPTION_MASTER_KEY (64-char hex = 32 bytes) encrypts OpenRouter API keys via AES-GCM. Never returns plaintext via HTTP — decrypted in-process only at request time.

▶ 2.1 Customer Support Resolution Agent Official

System: Inbound customer messages → intent classification → routing → response generation → optional human escalation.

Key Design Decisions

  • Multi-turn memory: Stateless API + external store. See conversations + conversation_messages tables — same pattern.
  • Escalation triggers: Confidence threshold below X%; negative sentiment detected; topic outside KB; customer explicitly requests human.
  • Tools: lookup_customer(id), search_knowledge_base(query), create_ticket(customer_id, summary), check_order_status(order_id)

Trade-offs

DecisionTrade-off
Parallel tool calls (lookup + KB search)Lower latency, but harder to debug partial failures
Always escalate after 3 failed attemptsSafer UX, but increases human load
Sliding window for historySimple, but forgets long-running issue context
Gotcha: Don't conflate "response sent" with "issue resolved". Measure outcomes (resolution rate, CSAT, re-open rate) not output (response sent). An agent that always sends a response with 0% resolution is worse than nothing.
Project: Conversation threading (conversations + conversation_messages) + per-model rate limiting directly maps to multi-turn support agent architecture.
▶ 2.2 Code Generation with Claude Code Official

System: Claude Code agentic CLI operates on a real codebase — plan → implement → test → iterate.

Key Design Decisions

  • CLAUDE.md as contract: Defines what Claude can/can't do. Constraints in CLAUDE.md are stronger than ad-hoc prompts — Claude reads it at session start and respects it throughout.
  • Permission model: allowed-tools in command frontmatter whitelists which tools the agent can use. Never wildcard in production.
  • Diff review gate: Never blindly accept generated code. Always review diff before apply. Hooks can enforce this (PostToolUse to display diff).

CI Integration Pattern

- name: Claude Code Review
  run: |
    claude -p --allowedTools=read,grep,diff <<'EOF'
    Review changed files. Flag: SQL injection, missing auth, N+1 queries.
    Files: ${{ github.event.pull_request.changed_files }}
    EOF
Gotcha: Agents accumulate context — long sessions drift. CLAUDE.md constraints can weaken as context grows. Start fresh context for fresh tasks. Don't let one session span 50 iterations.
▶ 2.3 Multi-Agent Research System Official

System: Orchestrator fans out to N specialist subagents in parallel, aggregates and synthesizes results.

Architecture Pattern

Orchestrator: plan → delegate → aggregate → synthesize
  ├─ Researcher-1: search_web(topic_A) + fetch_url(source_A)
  ├─ Researcher-2: search_web(topic_B) + fetch_url(source_B)
  └─ Analyst:      analyze_data(datasets) + run_query(sql)

Critical Rules

  • Trust boundary: Treat subagent output as untrusted input to orchestrator. Validate and cross-check. A subagent can hallucinate citations.
  • Deduplication: Multiple researchers may find same source. Hash-based dedup before synthesis.
  • Citation integrity: Always verify URLs exist before presenting as cited sources.
Gotcha: Serial subagent chains multiply latency. Design for parallelism from the start — retrofitting is hard. If subagent A must finish before B starts, ask if B actually depends on A's result or just happens to run second.
Exam trap: Orchestrator should NOT expose subagent tools to avoid confusion and context bloat. Orchestrator delegates via messages; subagents execute and report back.

Independent Review — Avoiding Cognitive Anchoring

  • Agent A generates review → Agent B sees Agent A's reasoning → B verifies it → Result: B is biased by A
  • Agent A generates review (A keeps its reasoning) → Agent B receives ONLY the raw input → B analyzes independently from scratch → compare conclusions
Why it matters: Cognitive anchoring makes B's "verification" worthless — it becomes a rubber stamp, not a check. Genuine independent review means B never sees A's output before forming its own conclusions.
▶ 2.4 Agentic Tool Design Official

Tool Design Checklist

  • Naming: verb_object convention. search_documents not doSearch or findDocsByKeyword.
  • Description: Written for the model, not humans. Include what it returns: "Returns document snippets matching query." Not "This tool searches things."
  • Schema: Strict types. Enums over free strings. Explicit required array. No vague "type":"any".
  • Idempotency: State-mutating tools (create, delete) must be safe to retry. HTTP PUT > HTTP POST for idempotency.
  • Error responses: Structured, actionable, not generic. "Error: DB timeout. Retry after 60s." not "Error".
Project tie-in: PUT /api/user/models/{id}/toggle — integer PK in path instead of string model ID. Why? Model IDs contain /; Tomcat normalizes URL-encoded slashes before Spring MVC routing. This is production agentic tool design — always design around transport constraints, not just business logic.

Idempotency Pattern

-- Atomic upsert for toggle (this project's implementation)
INSERT INTO user_model_preferences (user_id, model_id, enabled)
VALUES (?, ?, TRUE)
ON DUPLICATE KEY UPDATE enabled = NOT enabled;
-- Race-condition-safe: no load-then-store pattern
▶ 2.5 Developer Productivity with Claude Official

System: Code review automation, codebase Q&A (RAG), documentation generation.

Key Patterns

  • Codebase RAG: Embed codebase → store in vector DB → retrieve relevant chunks → generate answer. Quality of retrieval determines quality of answer.
  • Code review: Claude can catch: SQL injection, missing null checks, N+1 queries, hardcoded secrets, missing auth. Cannot replace human judgment for: business logic correctness, UX decisions, architectural trade-offs.
  • Choosing surface: IDE extension for inline suggestions, Claude Code CLI for multi-file refactors, API directly for CI pipeline automation.
Gotcha: Claude's knowledge of your codebase is only as fresh as what you give it. Stale context = stale answers. For large codebases, retrieval-augmented approaches beat stuffing everything in context.
▶ 2.6 Long Document Processing Official

System: Process documents too large for one context window. Chunking + map-reduce pattern.

Chunking Strategies

StrategyWhen to useGotcha
Fixed-size (512 tokens)Uniform documents, quick setupSplits mid-sentence, loses context at boundaries
Semantic (paragraph/section)Structured documents (contracts, reports)Uneven chunk sizes complicate batching
Hierarchical (chapter → section → para)Long-form content with clear structureComplex to implement, hard to preserve cross-chunk entities

Map-Reduce Pattern

Map phase:    [chunk_1, chunk_2, ... chunk_N] → parallel summaries
Reduce phase: summaries → synthesize into final output
Gotcha: Claude reads the whole context window every call. Stuffing a 150K-token document pushes your system prompt and conversation to the edges of the window. Claude's attention degrades on content in the middle of very long contexts ("lost in the middle" effect).
For retrieval vs. stuffing: if the user's question is answered by a small portion of the document, retrieve → generate. Only stuff if you need global understanding of the entire document.
▶ 2.7 Claude for Operations Extended

System: On-call assistant — alert triage, runbook automation, remediation suggestions.

Key Patterns

  • Alert triage: Classify severity → suggest remediation → escalate with context
  • Runbook tools: query_metrics(service, time_range), read_logs(pod, lines), trigger_rollback(deployment_id)
  • Safety gate (critical): Destructive ops (rollback, restart, scale-to-zero) require explicit human confirmation before execution. Never autonomous.
Gotcha: Ops agents need strict output validation — a hallucinated kubectl delete pod command is dangerous. Never execute LLM-generated shell commands without validation and human review. Parse intent, not raw output.
Project tie-in (Phase 5.0): POST /api/agent/chat is a read-only ops agent: asks questions about model enable/disable state and today's usage statistics. Tools are read-only (get_model_status, get_gateway_stats) — no mutation, so no human confirmation gate is needed. Admin-only access is the blast-radius guard. This is the "safest" class of ops agent: observe but never act.
▶ 2.8 Claude Code for Continuous Integration Extended

System: Non-interactive Claude Code in CI pipelines — code review, security scanning, automated fixes.

Non-Interactive Mode

  --allowedTools=read,grep,bash \    # minimal whitelist

▶ 2.9 Structured Data Extraction Extended

The Right Pattern

response = client.messages.create(
    tools=[{
        "name": "save_contacts",
        "description": "Save extracted customer contact data",
        "input_schema": {
            "type": "object",
            "properties": {
                "contacts": {
                    "type": "array",
                    "items": {
                        "type": "object",
                        "properties": {
                            "name":  {"type": "string"},
                            "email": {"type": "string", "format": "email"},
                            "phone": {"type": "string"}
                        },
                        "required": ["name", "email"]
                    }
                }
            },
            "required": ["contacts"]
        }
    }],
    tool_choice={"type": "tool", "name": "save_contacts"},  # force it
    messages=[{"role": "user", "content": document_text}]
)
contacts = response.content[0].input["contacts"]  # always valid JSON

Handling Ambiguity

  • Field unclear in source → return null, not a guess
  • Add confidence field (0.0–1.0) for downstream routing
  • Low confidence → route to human review queue
  • Batch: process records in parallel, isolate failures per-record
Project tie-in: chat_logs table is an extraction target contract — Flyway schema as the JSON schema analog. MarkdownNormalizer extracts structured content from raw LLM output for storage.

▶ 2.11 Agent Skills — Enterprise Knowledge Management Extended

System: RAG pipeline over internal knowledge — SharePoint, Confluence, Slack, wikis.

RAG Pipeline

Ingestion:  Crawl sources → chunk → embed → store in vector DB
Query:      User question → embed → similarity search → retrieve top-K
Generation: Retrieved chunks + question → Claude → answer with citations

Critical Issues

  • Access control: Retrieved context must respect source permissions. If user can't see document, don't retrieve it into their context.
  • Freshness: Embeddings go stale. Define an index update strategy: full re-embed weekly, incremental updates on change.
  • Multi-source fusion: Conflicting facts from different sources — surface both, let user decide.
Gotcha: Retrieval quality determines answer quality. Garbage embeddings → garbage answers. Most RAG failures are retrieval failures, not generation failures. Test retrieval in isolation first.
▶ 2.12 Agent Skills — Developer Tooling Extended

System: MCP servers wrapping internal developer tools — JIRA, GitHub, CI systems.

Key Patterns

  • OAuth delegation: MCP server requests token on behalf of user. Never hardcode service account tokens that bypass user permissions.
  • Tool composition: Agent chains: search_issues → get_issue_detail → create_pr → link_pr_to_issue. Each tool is atomic; agent chains them.
  • Tool count: Keep each MCP server focused (4–5 tools). Split by domain: mcp-github (issues, PRs), mcp-jira (tickets, sprints), mcp-ci (builds, deployments).
This project's environment: Jira MCP connector is available. Real example of an MCP server wrapping an internal API with auth delegation and bounded tool surface.
▶ 2.13 Agent Skills — Code Execution Extended

System: Agent generates and executes code. Sandbox is critical.

Security Requirements

  • Execute untrusted code in host environment (RCE risk)
  • Allow pip/npm install (supply chain risk)
  • Unrestricted filesystem/network access in sandbox
  • Isolated container per execution (Docker, gVisor, Firecracker)
  • Read-only filesystem except declared output dirs
  • Network egress blocked or limited to allowlist
  • CPU/memory/time hard limits per execution
  • Declare allowed languages/runtimes; reject others

Output Capture Pattern

result = sandbox.run(
    code=block.input["code"],
    language=block.input["language"],
    timeout_s=30,
    max_memory_mb=512
)
tool_result = {
    "stdout": result.stdout[:5000],  # cap output size
    "stderr": result.stderr[:1000],
    "exit_code": result.exit_code,
    "truncated": result.truncated
}
Gotcha: Agents will attempt to install packages (pip install requests, npm install lodash). These must be blocked at the sandbox level, not just by prompt instruction.

§4 Judgment Heuristics — For Unexpected Scenarios Apply these when you haven't studied the exact scenario ▶

The 6 Questions — Ask for Every Question

1. Who is the user?

End user, developer, internal ops, or another agent? Different principals have different trust levels and blast radii.

2. What can go wrong?

Hallucination, prompt injection, data leakage, runaway costs, latency blowup, inconsistent state?

3. What's the blast radius?

Read-only vs. mutating? Reversible vs. irreversible? Single-user vs. system-wide impact?

4. Is an agent needed?

Or is a single well-prompted API call sufficient? Simpler is almost always better.

5. How do you evaluate success?

Define the metric before designing the system. Resolution rate, CSAT, token cost, latency P99?

6. What breaks at scale?

Context window, latency, cost, rate limits, data consistency, parallel agent conflicts?

SPIDER — 6 Reliability Principles

Memory hook: S, P, I, D, E, R = SPIDER. Apply to every agent, tool, and pipeline you design.

LetterStands ForKey Point
SStructuredUse schemas, validation rules, deterministic constraints — not natural language wishes
PPersistentStore state (decisions, history, audit trail) so you can resume and verify what happened
IIdempotentSame input run twice = same result. No double charges, no duplicate records
DDeterministicSame input → same output always. No randomness in critical paths (tool calls, decisions)
EEscalationWhen you can't resolve with certainty, escalate to human. Don't guess, don't try harder
RResilientRetry with backoff, handle transient failures gracefully, degrade if needed

CALM Framework (D5)

Prompt Caching Cost Math

Cache write:  +10% cost (first request pays to populate cache)
Cache read:   10% of normal cost (subsequent requests)

Example — 2 requests, 10K cached tokens:
Request 1: 10K normal + (10K × 10%) cache-write = 11K effective cost
Request 2: (10K × 10%) cache-read = 1K effective cost
Total: 12K vs 20K without caching = 40% savings

Rule: Cache system + tools (stable). Never cache conversation (changes every turn).
Max 5 cache breakpoints per message.
§5 Key ADRs — Exam-Relevant Architectural Decisions Real trade-offs from this project (through Phase 5.0) · Every one maps to a CCA-F concept ▶

These are not hypothetical. Every row is a real decision made building this gateway — and maps directly to the kind of trade-off reasoning the exam tests. Rows marked (PRD-005) are from Phase 5.0 — the Gateway Intelligence Agent (ReAct loop, SSE streaming, retry candidate list).

DecisionWhy it matters (exam angle)
Flyway instead of ddl-auto=update Schema is production data. Migrations must be auditable, versioned, and repeatable. ddl-auto=update makes schema changes implicit and untracked — wrong for any production LLM system that has chat logs and user data.
Integer PK in tool path, not string modelId Design tools around transport constraints. Model IDs contain /. Tomcat normalizes URL-encoded slashes before Spring MVC routing. Using integer PK is the correct agentic tool design decision.
SSE tokens JSON-encoded, not raw strings Protocol gotcha. Raw \n in SSE data: field is treated as event separator — silently drops newlines from streamed content. JSON-encode on backend, JSON.parse on frontend.
AES-GCM for stored API keys, not BCrypt Wrong hash function breaks functionality. BCrypt is one-way (verify only). API keys must be decrypted to use for upstream calls. AES-GCM is the only correct choice here.
Bucket4j per-user rate limiting Global limits punish well-behaved users. Per-user isolation is fairer and safer — one bad actor can't exhaust system quota. Per-model limits add cost gates for expensive models.
Request limit pre-call, token limit post-call Two-phase enforcement is the only correct model. Token count is unknown before call completes. Check request count (known) before call; check token count (measured) after.
nginx Authorization pass-through (BYOK) Per-user attribution requires forwarding the user's key. Injecting a system key into every request hides which user made the call — defeats per-user tracking and BYOK model.
Sparse preference table (absence = enabled) Scalable default. Pre-populating every user×model row doesn't scale. Sparse table with absence-means-enabled requires no migration when new models are added.
@Transactional on lazy collection access Hibernate session lifecycle. Session closes after each repository call. Accessing lazy collections outside a transaction causes LazyInitializationException. Missing this annotation causes production failures.
ASYNC dispatcher must permitAll() SSE-specific Spring Security gotcha. SseEmitter.complete() triggers an async re-dispatch. Spring Security intercepts it with no SecurityContext and throws Access Denied. Fix: .dispatcherTypeMatchers(DispatcherType.ASYNC).permitAll().
Upstream 404 auto-disables model Graceful degradation. When OpenRouter returns 404 for a model (removed from free tier), automatically disable it in DB rather than letting every subsequent call fail. Ops-grade LLM system must self-heal on model changes.
Atomic upsert for model toggle Concurrent write safety. Load-or-create pattern has race condition: two concurrent inserts violate unique constraint, or last-write-wins produces wrong toggle state. INSERT ... ON DUPLICATE KEY UPDATE enabled = NOT enabled is atomic.
Agent uses BYOK key; 409 if none set Enforcement at the right layer. POST /api/agent/chat raises KeyNotConfiguredException → HTTP 409 when no stored API key exists. Never fall back to a system key for agent calls; that breaks per-user attribution and cost tracking. (PRD-005)
Agent retry loop: candidate list, not single model Graceful degradation for free-tier instability. AgentService builds a candidate list (requested model first, then all DB-enabled models). On ModelRateLimitedException or ModelToolUseNotSupportedException it logs WARN and tries the next candidate. All exhausted → 503. This is the production pattern for unreliable upstream models — relevant to every agentic scenario in the exam. (PRD-005)
MAX_TURNS = 10 hard guard in AgentService Runaway loop prevention. Without a turn cap, a misbehaving model can issue tool_use repeatedly, consuming unlimited tokens and latency. MAX_TURNS is the minimum viable safety gate for any ReAct agent in production. The exam tests this: "What prevents an agentic loop from running indefinitely?" — answer: max-turns guard + budget enforcement. (PRD-005)
Agent SSE: fetch + ReadableStream, not EventSource EventSource only supports GET. The agent endpoint requires POST (carries request body with model, question, history). EventSource cannot POST — use fetch + ReadableStream and parse event:/data: lines manually. Classic CCA-F trap: "use SSE for streaming" is correct; "use EventSource for SSE" is wrong when POST is required. (PRD-005)
gotDone flag, not finalReply truthiness Empty-text final turn is valid. Some models issue a tool_use block as the last turn with no accompanying text. Frontend must check gotDone alone when deciding to render the agent reply; never gate on finalReply being truthy. Gating on text presence silently drops valid responses. (PRD-005)
ResourceAccessException → ModelRateLimitedException (25 s timeout) Timeout = transient = retryable. OpenRouterAdapter has a 25 s read / 5 s connect timeout. A timeout throws Spring's ResourceAccessException, caught and re-thrown as ModelRateLimitedException so the retry loop treats it identically to a 429. Never let timeouts escape as unhandled exceptions inside an agentic retry loop. (PRD-005)
OpenRouterAdapter isolates OpenAI ↔ Claude API format Single responsibility for protocol adaptation. AgentService speaks Claude API format exclusively (stop_reason, tool_use blocks, tool_result blocks). Only OpenRouterAdapter knows about OpenAI format. Swapping providers = replace adapter only. This is the MCP adapter pattern at the service layer — directly maps to D2 tool-design isolation. (PRD-005)
ModelRateLimitedException is retry-internal, never HTTP Internal signal, not client error. ModelRateLimitedException is only caught inside AgentService.run(). The global exception handler handles AllModelsUnavailableException (→ 503) and ModelToolUseNotSupportedException (→ 400) only. Leaking an internal retry signal as a client-facing HTTP status is an API design anti-pattern. (PRD-005)
